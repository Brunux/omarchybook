# v0.1.1 — Omarchy on the Google Hayato

The second release of the port: **Arch Linux ARM + Omarchy v4 (`quattro`)** on the **Google Hayato
rev1** (ASUS Chromebook Detachable / Flip CM3 CM3200 — MediaTek MT8192 "Asurada", `google-asurada`),
booting from a microSD card or the eMMC with the stock ChromeOS firmware in place and no UEFI,
through the same **signed depthcharge FIT `kpart`** v0.1.0 boots with. The stack, the hardware
support and the limitations are v0.1.0's; what is new is the port's own naming, the installer the
*device* ships, and the fixes the first real release build and the first physically flashed card
turned up. `docs/releases/v0.1.0.md` is still the long description of what this system is — the
Omarchy pin (`4.0.0.r7026.g51bfd1d`, channel `edge`), the kernel (`linux-omarchy-book` 7.2.7),
the desktop (`SDDM → uwsm → Hyprland on Panfrost → Quickshell`), the Hayato quirks and the
accounts with passwords.

## What changed since v0.1.0

- **The platform packages are renamed**: `omarchy-google` → **`omarchy-book`** and
  `omarchy-google-boot` → **`omarchy-book-boot`**, installed at `/usr/lib/omarchy/book{,-boot}` with
  the dispatcher's binaries at `/usr/bin/omarchy-book-*` and the group `omarchy-platform-book`. The
  name is the kernel's own brand — `linux-omarchy-book` — so kernel and platform read as one family
  (plan §3). Both packages still `provides`/`conflicts` `omarchy-platform`, which is what lets a
  package manager replace one with the other. Both are **`0.1.0-1`**, their first version under the
  new names; the two `-dev` packages below are what moved. Unchanged on purpose: the
  `aarch64-google` family, the device directory `devices/google-asurada/`, the detector
  `bin/omarchy-hw-aarch64-google` and `install/hardware/google/`.

- **The installer the device ships follows pmbootstrap's path** (`boot/lib-cgpt.sh`, in
  `omarchy-book-boot`; the same file `write-sd.sh`, `install-emmc.sh`, `make-image.sh` and
  `restore-system.sh` use). The port had inherited bugs that bite the eMMC, and they are fixed here:
  p3 ends 33 sectors before the end of the device, not 2048; a mounted partition is refused before it
  is wiped; the partitions are resolved by `PARTN`, not by their position in `lsblk` (the kernel
  reorders them); the mount points `rsync` drops are recreated and the card's identity is not cloned;
  `/etc/fstab` gets pmbootstrap's options with the root's `errors=remount-ro` kept; and
  `install-kpart.sh` carries `CONFIRM`/`DEVICE` through its `sudo` re-exec.

- **`omarchy-dev` and `omarchy-settings-dev` are `pkgrel=2`.** They are rebuilt with new bytes —
  the lifecycle dispatcher resolves to `omarchy-book` — and a package a release already carries gets
  a `pkgrel` bump before it is republished, or a machine holding that version will not move to it
  (plan §3 decision 8). `build-omarchy.sh`'s rebuild stamp now hashes the vendored recipes as well,
  so a bump actually triggers the rebuild it needs.

The release tooling changed too, and it does not travel in the image: the build chroot is marked by
its keyring and its `resolv.conf` is written without ALARM's dangling symlink
(`scripts/build-omarchy.sh`, `build-package.sh`, `build-rootfs.sh`); and `SHA256SUMS` lists only
what is published — the uncompressed image is a build by-product and is neither shipped nor hashed
(`scripts/make-release.sh`, `docs/recon.md` §13).

## Validation

The boot chain and the installer are verified the way they can be off the device: on a loop device
(the geometry, the mounted-partition and small-`/boot` refusals, the generated `/etc/fstab`), end to
end with `make-image.sh` against a fixture rootfs, and by `futility show` on the signed FIT the
image carries. What is *not* claimed here is a boot of this image: v0.1.0's validation on real
hardware — three cards, the reports kept in `reports/` — was of the image that release carried, and
the card that boots v0.1.1 is what confirms the rename and the installer fix. That report, with no
FAIL, is what Phase 7's acceptance still waits for (`docs/recon.md` §14).

## Assets

| asset | what it is |
|---|---|
| `google-asurada.img.xz` | the disk image: the three ChromeOS GPT partitions (kernel, `/boot`, root), ready for `dd` |
| `google-asurada-rootfs.tar.zst` | the same root filesystem as a tarball, for writing your own card with `scripts/write-sd.sh` |
| `google-asurada.vmlinuz.kpart` | the signed FIT kernel partition of *that* image; it embeds the image's `root=UUID=`, so it belongs to this image and no other |
| `platform.tar.zst` | the `[platform]` bundle as a repository: the signed kernel, `omarchy-book`/`omarchy-book-boot` and their `-dev` counterparts, with their `.sig`, the database, `platform.pub` and its README |
| `RELEASE-INFO.txt` | what this build was made of: commit, tag, kernel, Omarchy commit, hashes |
| `SHA256SUMS` | SHA-256 of the other assets, which is the published set and nothing else |

```sh
sha256sum -c SHA256SUMS
xz -dc google-asurada.img.xz | sudo dd of=/dev/mmcblk1 bs=4M conv=fsync
```

The two large assets are published **in parts**, because a single file in a GitHub release must be
under 2 GiB and this system is bigger than that: `google-asurada.img.xz` and
`google-asurada-rootfs.tar.zst` arrive as `…part-aa`, `…part-ab`, and so on. Reassemble them before
use — `SHA256SUMS` holds the hash of the whole file, so the check catches a part that came down
wrong or is missing:

```sh
cat google-asurada.img.xz.part-* > google-asurada.img.xz
cat google-asurada-rootfs.tar.zst.part-* > google-asurada-rootfs.tar.zst
sha256sum -c SHA256SUMS
```

On the Chromebook: developer mode, `crossystem dev_boot_usb=1 dev_boot_signed_only=0`, insert the
card and press **Ctrl+U** — the eMMC is depthcharge's default. To write the eMMC from the running
system, `scripts/install-emmc.sh`; to write a card from the tarball,
`sudo ROOTFS=<extracted dir> scripts/write-sd.sh <card>`.

## How an installed machine moves forward

The image still configures **no `[platform]` repository**: this release is not served anywhere yet,
so the way forward is a new image. The bundle travels in `platform.tar.zst` for anyone who wants to
install a package by hand (`sudo pacman -U ./platform/<package>`) or to serve the directory and
point the device at it (one `[platform] Server =` line under `[omarchy]` in `/etc/pacman.conf`,
which is the `PLATFORM_REPO_URL` build input). The trust is already in place: every image of this
port trusts the bundle's signing key.

Because the platform packages changed name, a machine that already carries `omarchy-google` and
`omarchy-google-boot` takes the new pair by installing `omarchy-book` and `omarchy-book-boot`
(the two share `omarchy-platform`, so one replaces the other) — and it takes `omarchy-dev` with them,
because the dispatcher it installs is the one that resolves to `omarchy-book`. Upgrading only one
half leaves the lifecycle pointing at a package that is not there.

## Passwords

Every image of this port carries accounts with a password set, and the release notes are where that
is said out loud:

- `root` / `root` (uid 0) and `alarm` / `alarm` (uid 1000, in `wheel`), as Arch Linux ARM ships
  them — leaving `alarm` in place is a deliberate decision (plan §3, decision 8), not an oversight;
- `omarchy` / `omarchy` (uid 1001, in `wheel`, and the account the desktop session logs in with).

**Change them, or lock them, before the machine sees a network.** `make-release.sh` prints them at
publish time for the same reason.

## Everything else is v0.1.0

The first boot's deferred setup (the second `video` group membership and an initramfs rebuild, about
a minute and a half, after which the greeter asks for `omarchy`'s password), what the image and the
tarball are sanitized of (no Wi-Fi profiles, no SSH host keys, no `machine-id`, no build state) and
the known limitations (no LUKS and none of Omarchy's factory-reset or re-key paths; no
UEFI/GRUB/Limine; the `sbs`/`mt6359`/BPF-LSM noise this hardware makes; 4 GB of RAM; Chromium on ARM)
are unchanged from v0.1.0 and written down there, with the hardware reports in `reports/` and the
measurements behind them in `docs/recon.md`.
