# v0.1.0 — Omarchy on the Google Hayato

The first release: **Arch Linux ARM + Omarchy v4 (`quattro`)** on the **Google Hayato rev1** (ASUS
Chromebook Detachable / Flip CM3 CM3200 — MediaTek MT8192 "Asurada", `google-asurada`), booting from
a microSD card or the eMMC with the stock ChromeOS firmware in place and no UEFI. The boot chain is
the one the sibling Debian port (**Nureb**) proved on this hardware — a **signed depthcharge FIT
`kpart`** in the ChromeOS kernel partition, resolved from `kern_guid` and the device tree. What is
new underneath it is the distribution.

## What is in it

- **Arch Linux ARM, `aarch64`**, bootstrapped from ALARM's tarball, plus the packages Omarchy's own
  repositories cannot carry for this device.
- **Omarchy 4.0.0.r7026.g51bfd1d** — upstream `quattro` at `51bfd1d`, channel **`edge`** — with this
  port's `aarch64-google` patch: the detector recognises the `google,` device-tree vendor prefix,
  the lifecycle dispatcher registers the platform, and the hardware leaves live in
  `install/hardware/google/`.
- **Linux 7.2.7** (`7.2.7-mt81`), mainline plus the MT8192 device trees and patches proven in Nura,
  packaged as **`linux-omarchy-book`** and held at this version with `IgnorePkg` so `omarchy update`
  cannot pull Omarchy's own kernel back in.
- **`omarchy-google`** (runtime and platform layer) and **`omarchy-google-boot`** (the ChromeOS GPT
  and the signed kpart), plus `depthcharge-tools` from the `[platform]` bundle.
- **The desktop**: SDDM → uwsm → Hyprland on Panfrost → the Omarchy Quickshell shell, with Omarchy's
  Hyprland configuration seeded from `/etc/skel` the way `useradd -m` would seed it.
- **The Hayato quirks**: `keyd` remapping (Search as Super, the Lock key), the MT8192 ALSA UCM boot
  sequence, RTW88 firmware, the group-writable backlight udev rule, and zram swap.

## Validation

This is not an "it builds" release. Three cards have booted on hardware, and their reports
(`scripts/check-system.sh`, run from the desktop session, with `scripts/collect-diagnostics.sh`
beside a report that needs explaining) are kept in `reports/`; every FAIL is mapped to a measured
cause in `docs/recon.md` §14.

The third card is the state this image carries: **108 ok, 1 warn, 1 FAIL, 0 skip**. It is the first
one whose session is complete — SDDM logs in, Hyprland runs, the Quickshell shell is up, Omarchy's
Hyprland configuration is in place, `omarchy-sleep-lock.service` is enabled and swap is up a second
after boot — because the two cards before it found real bugs that are fixed in this image: the SDDM
owner state upstream's wizard would have written (without it the greeter can never log in), the
`[platform]` signing key a first boot's own `pacman-key --populate` would otherwise replace, and the
`/etc/skel` seed the account never got.

Its one FAIL was the report's own probe rather than the machine: `pgrep -x` cannot match
`omarchy-system-sleep-monitor`, because the kernel truncates a process name to 15 characters
(measured), so the monitor was asked for with a name that can never match it. The check asks systemd
for `omarchy-sleep-lock.service` now, and the next report is what confirms it. Its one warn made the
same kind of assumption, about a Wi-Fi profile the maintainer had created on the machine; the check
now warns only for a profile the image itself shipped.

## Assets

| asset | what it is |
|---|---|
| `google-asurada.img.xz` | the disk image: the three ChromeOS GPT partitions (kernel, `/boot`, root), ready for `dd` |
| `google-asurada-rootfs.tar.zst` | the same root filesystem as a tarball, for writing your own card with `scripts/write-sd.sh` |
| `google-asurada.vmlinuz.kpart` | the signed FIT kernel partition of *that* image; it embeds the image's `root=UUID=`, so it belongs to this image and no other |
| `platform.tar.zst` | the `[platform]` bundle as a repository: the signed kernel and platform packages with their `.sig`, the database, `platform.pub` and its README |
| `RELEASE-INFO.txt` | what this build was made of: commit, tag, kernel, Omarchy commit, hashes |
| `SHA256SUMS` | SHA-256 of the other assets |

```sh
sha256sum -c SHA256SUMS
xz -dc google-asurada.img.xz | sudo dd of=/dev/mmcblk1 bs=4M conv=fsync
```

The two large assets are published **in parts**, because a single file in a GitHub release must be
under 2 GiB and this system is bigger than that: `google-asurada.img.xz` and
`google-asurada-rootfs.tar.zst` arrive as `…part-aa`, `…part-ab`, and so on. Reassemble them before
use — `SHA256SUMS` holds the hash of the whole file, so the check catches a part that came down
wrong or is missing:

```sh
cat google-asurada.img.xz.part-* > google-asurada.img.xz
cat google-asurada-rootfs.tar.zst.part-* > google-asurada-rootfs.tar.zst
sha256sum -c SHA256SUMS
```

The list also carries `google-asurada.img`, the uncompressed image the build keeps for itself and
does not publish (11.8 GiB); to check exactly what you downloaded:

```sh
grep -v 'google-asurada\.img$' SHA256SUMS | sha256sum -c -
```

On the Chromebook: developer mode, `crossystem dev_boot_usb=1 dev_boot_signed_only=0`, insert the
card and press **Ctrl+U** — the eMMC is depthcharge's default. To write the eMMC from the running
system, `scripts/install-emmc.sh`; to write a card from the tarball,
`sudo ROOTFS=<extracted dir> scripts/write-sd.sh <card>`.

## How an installed machine moves forward

The image configures **no `[platform]` repository**: this release is not served anywhere yet, so the
way forward is a new image. The bundle travels in `platform.tar.zst` for anyone who wants to install
a package by hand (`sudo pacman -U ./platform/<package>`) or to serve the directory and point the
device at it (one `[platform] Server =` line under `[omarchy]` in `/etc/pacman.conf`, which is the
`PLATFORM_REPO_URL` build input). The trust is already in place: every image of this port trusts the
bundle's signing key. A republished package — same version, new bytes — gets a `pkgrel` bump before
it is released, or an installed machine will not move to it (`docs/recon.md` §9).

## Passwords

Every image of this port carries accounts with a password set, and the release notes are where that
is said out loud:

- `root` / `root` (uid 0) and `alarm` / `alarm` (uid 1000, in `wheel`), as Arch Linux ARM ships
  them — leaving `alarm` in place is a deliberate decision (plan §3, decision 8), not an oversight;
- `omarchy` / `omarchy` (uid 1001, in `wheel`, and the account the desktop session logs in with).

**Change them, or lock them, before the machine sees a network.** `make-release.sh` prints them at
publish time for the same reason.

## First boot

The image defers one part of the hardware setup (Omarchy's own install cannot do it under `chroot`
in every case, so the machine finishes it): the second `video` group membership and an initramfs
rebuild, which take about a minute and a half on the first boot. After that the greeter asks for
`omarchy`'s password. `scripts/check-system.sh` in this repository is the report that says whether
the machine came up as intended, and `reports/` is where the reports from real hardware live.

## What it does not carry

The image and the tarball are sanitized before they are compressed, and the release refuses to
publish while anything is left (`scripts/lib-dist.sh`):

- **no Wi-Fi profiles** — the build rootfs is where the maintainer's networks are imported, PSKs in
  clear; the released image knows no network and asks you for one;
- **no SSH host keys** — generated on first boot, so every installation has its own;
- **no `machine-id`** — systemd generates a fresh one on first boot;
- **no build state** — no pacman cache, no bootstrap tarball, no `[platform]` staging directory, and
  nothing of this repository's work directory.

## Known limitations

- **No LUKS**, and with it none of Omarchy's factory-reset or re-key paths; no snapper/btrfs
  snapshots. Both are non-goals for v0.1 (plan §1).
- **No UEFI/GRUB/Limine**, no Apple Silicon, Qualcomm or NVIDIA platform code.
- The **fuel-gauge noise** (`sbs-8-000b` failing to report properties), the `mt6359` `of_node`
  warnings and the `bpf-restrict-fs` BPF-LSM message are this hardware's, and are the same on the
  Debian port's verified machine.
- **4 GB of RAM** for Hyprland plus Quickshell: comfortable at 1920×1200, but the shell's heavier
  pieces are the ones to trim if it ever is not (plan §7).
- **Chromium on ARM** is a known weak spot; `brave-bin` is published for `aarch64`, and Chromium
  stays optional.
